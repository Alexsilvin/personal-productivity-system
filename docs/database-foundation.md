# Database foundation decisions

## Database technology

We use PostgreSQL with the native `pg` driver and explicit SQL migrations. This keeps the stack simple, transparent, and testable without introducing a full ORM. The database layer remains separate from business logic and stays easy to extend with transactions, repository code, and future migrations.

## Migration approach

Migrations are plain SQL files in the backend infrastructure folder. Each migration is applied once in order, and a `schema_migrations` table records which versions are already applied. This gives a clean path from an empty database to the current schema without hidden automation.

## ID strategy

We use UUIDs generated by PostgreSQL (`gen_random_uuid()`). This is a better fit for a future cloud-first, cross-platform system than auto-increment integers because the same identifiers remain stable across clients and environments.

## Timestamp strategy

All persisted timestamps are stored in UTC and are represented as `TIMESTAMPTZ`. User timezone is stored separately on the `users` table and treated as a user preference, not a persisted execution timestamp. This keeps the database consistent while allowing local time display in the future.

## Relationship and deadline decisions

The initial schema includes the core ownership model:

- `users` owns `goals`, `projects`, `courses`, and `tasks`
- `projects` can be linked to a goal
- `tasks` can be linked to a project, course, and goal

We intentionally did not create a separate `deadlines` table in this phase. The early V1 model already has `tasks.due_at`, `projects` and `goals` target dates, and future work can introduce a distinct external deadline model only if those distinctions become necessary. This avoids premature abstraction while preserving a clear path for later scheduling logic.


# Commands
```
# from repo root
docker compose up -d

# in backend
cp .env.example .env
npm install
npm run migrate
npm run dev
```

For database-specific verification when PostgreSQL is available:
```
RUN_DATABASE_TESTS=true npm test
npm run migrate:status
npm run build
npm run lint
```
